# incidents/ — 장애 기록

## 1. 개요

- 파이프라인이 실패했을 때 **현상 · 원인 · 조치사항**을 한 파일로 남김
- 개념 문서([docs/dbt/](../dbt/README.md) · [docs/airflow/](../airflow/README.md))가 "이 도구는 어떻게 동작하는가"라면,
  여기는 **"이 파이프라인이 실제로 어떻게 깨졌는가"**임
- 폴더 README의 `고려사항`은 설계 시점의 판단을 남기고, 여기는 운영 시점의 사고를 남김

| 날짜 | 제목 | 한 줄 |
|---|---|---|
| 2026-08-17 | [태스크가 실행되지 않고 즉시 실패](2026-08-17-airflow-task-never-launched.md) | 스케줄러 PATH에 venv가 없어 `airflow tasks run` 서브프로세스가 기동 실패 |
| 2026-08-17 | [fork 된 자식이 os_log 에서 멈추거나 죽는다](2026-08-17-macos-fork-unsafe-os-log.md) | macOS os_log 가 fork 안전하지 않음. 웹서버는 SIGSEGV, 태스크는 무한 스핀. `OS_ACTIVITY_MODE=disable` 로 후자 해결 |

## 2. 구성

각 기록은 아래 순서를 지킴.

| 절 | 내용 |
|---|---|
| 현상 | **관측된 것만.** 에러 메시지 원문, 실패 범위, 재현 조건 |
| 원인 | 증상에서 근본 원인까지의 연결 고리. 근거(로그·메타DB·코드 위치)를 함께 |
| 조치사항 | 지금 복구하는 법과, 재발을 막기 위해 코드·문서에 반영한 것 |

- 파일명은 `YYYY-MM-DD-영문-슬러그.md`
- **틀렸던 추정도 남김.** 무엇을 먼저 의심했고 왜 아니었는지가 다음 사람의 시간을 아낌

## 3. 고려사항

- **증상과 원인을 같은 칸에 적지 않음**
  - 이번 건이 그 예임. UI에 뜬 메시지(`No host supplied`)는 체인의 마지막 고리였고, 그것만 보고는 원인에 닿지 못함
  - 현상 절에는 **본 것만** 적고, 해석은 원인 절로 미룰 것

- **메타DB를 근거로 남김**
  - Airflow는 태스크가 기동조차 못 하면 로그 파일을 만들지 않음. 그때 유일한 증거가 메타DB임
  - 어떤 쿼리로 무엇을 확인했는지 함께 적어야 다음에 재현할 수 있음
