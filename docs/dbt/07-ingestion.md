# dbt 앞단 — 원천에서 DW로

> dbt  ·  [← 모델을 추가하는 절차](06-workflow.md) | [목차](README.md) | [실전 운영 →](08-operations.md)

dbt 가 시작되기 전 구간. 추출 전략 3종, 워터마크 증분의 함정, Data Lake 랜딩, 스키마 드리프트를 다룸.

## 7-1. 추출 전략 — 전체 스냅샷 vs 증분 vs CDC

### 7-1-1. 정의

| 방식 | 동작 | 조건 | 함정 |
|---|---|---|---|
| **전체 스냅샷** | 매번 전체를 읽어 통째로 교체 | 테이블이 작을 때 | 커지면 원천 부하·시간 폭증 |
| **증분 (워터마크)** | `updated_at > 마지막 처리값`만 읽음 | 신뢰할 만한 갱신 시각 컬럼 필요 | **삭제를 감지 못 함.** 경계값 처리 |
| **로그 기반 CDC** | DB 트랜잭션 로그를 읽어 변경을 스트리밍 | 원천 DB의 로그 접근 권한 필요 | 운영 부담, 초기 스냅샷 필요 |

- **CDC 도구**: Debezium(오픈소스), AWS DMS, Datastream(GCP), Fivetran·Airbyte(관리형)

- **CDC의 진짜 장점은 "삭제와 중간 변경을 잡는다"는 것임**
  - 워터마크 방식은 행이 지워지면 알 방법이 없고, 같은 행이 하루에 세 번 바뀌어도 마지막 상태만 봄


## 7-2. 워터마크 증분의 함정

### 7-2-1. 정의

- `updated_at > last_value`는 단순해 보이지만 실무에서 자주 깨짐

| 함정 | 내용 | 대응 |
|---|---|---|
| **경계값** | `>` 면 같은 시각의 행 누락, `>=` 면 중복 | 중복을 허용하고 **멱등하게** 처리 |
| **시계 오차** | 원천 서버 시각과 추출 시각이 다름 | 안전 마진(lookback) 확보 |
| **트랜잭션 지연** | 커밋은 늦었는데 `updated_at`은 과거 | lookback 윈도우 |
| **삭제 미감지** | 지워진 행은 조회되지 않음 | soft delete 또는 주기적 전체 대조 |
| **updated_at 미갱신** | 애플리케이션이 안 건드리는 경로 존재 | 원천 팀과 계약, CDC로 전환 |

```sql
-- 잘못된 방식 — 경계값에서 행이 샌다
--    같은 초에 여러 건이 커밋되면 last_value 와 같은 시각의 행이 누락된다
select * from source where updated_at > '2026-08-15 03:00:00'

-- 올바른 방식 — 겹치게 읽고 멱등하게 덮는다
--    중복은 파티션 교체나 MERGE 로 흡수한다
select * from source
where updated_at >= timestamp_sub('2026-08-15 03:00:00', interval 3 day)
```

- **lookback 윈도우가 푸는 것은 위 다섯 중 셋임**
  - 경계값 · 시계 오차 · 트랜잭션 지연 — 전부 **"이미 지나간 구간에 행이 뒤늦게 나타나는"** 문제라 겹쳐 읽으면 채워짐
  - 나머지 둘은 성격이 다름. **삭제 미감지**는 조회 자체가 안 되므로 겹쳐 읽어도 안 잡히고,
    **`updated_at` 미갱신**은 기준 컬럼을 못 믿는 것이라 워터마크 방식 자체가 성립하지 않음

> **lookback 은 "시점 재현"과 다른 문제를 푼다.** 겹쳐 읽는 것은 **누락된 행을 줍는** 장치이지,
> "T 시점의 상태를 복원하는" 장치가 아님.
> 값이 바뀌는 테이블에 lookback 을 걸면 과거 파티션이 **현재 값으로 덮이므로**
> 오히려 그때 상태가 사라짐.
> 특정 시점 상태가 필요하면 CDC 나 이력 보존으로 가야 함(1-6, 7-1 참조).

- **append-only 인지 mutable 인지가 먼저임**

  | 원천 성격 | 워터마크 증분 | 이유 |
  |---|---|---|
  | append-only (이벤트·로그) | **적합** | 행이 한 번 쓰이고 바뀌지 않음 |
  | mutable master (회원·상품·재고) | **부분적** | 최신 상태만 얻음. 과거 상태는 재현되지 않음 |



## 7-3. Data Lake 랜딩 — 포맷과 레이아웃

### 7-3-1. 정의

**포맷**

| 포맷 | 특성 | 용도 |
|---|---|---|
| **Parquet** | 컬럼나, 압축률 높음, 스키마 내장, predicate pushdown | **랜딩 표준** |
| Avro | 행 기반, 스키마 진화에 강함 | 스트리밍 수집 |
| JSON/CSV | 사람이 읽기 쉬움, 비효율 | 소량·디버깅용 |

- **레이아웃** — 보통 수집일 기준으로 파티션을 나눔

```
s3://lake/raw/orders/ingest_date=2026-08-14/part-0000.parquet
```

**중요한 원칙 두 가지**

- **랜딩은 불변(immutable)임**
  - 재처리는 파티션 교체로 하고 행 단위로 고치지 않음
  - (DW의 Non-Volatile 특성, Medallion의 Bronze와 같은 원칙)
- **작은 파일 문제**를 조심함
  - 파일이 잘게 쪼개지면 메타데이터 오버헤드로 읽기가 느려짐
  - → 분산처리 관점은 `docs/tech/bigdata.md` 참조


## 7-4. Lake와 DW를 잇는 방법 — 외부 테이블 vs 적재

### 7-4-1. 정의

| 방식 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **적재(Load)** | Lake 파일을 DW 스토리지로 복사 | 빠름, 최적화된 포맷 | 중복 저장, 적재 시간 |
| **외부 테이블** | DW가 Lake 파일을 직접 조회 | 복사 없음, 즉시 반영 | 느림, 일부 기능 제약 |

**BigQuery의 선택지**
- **External Table** — GCS 파일을 직접 조회
  - 임시·저빈도 조회용
- **BigLake** — 외부 테이블에 세밀한 접근 제어(행·컬럼 수준)를 얹음 → `docs/tech/data-security.md` *(작성 예정)*
- **BigQuery Iceberg 테이블** — 개방형 테이블 포맷 지원

```sql
-- BigQuery 외부 테이블 — GCS 파일을 복사 없이 조회한다
create or replace external table `proj.raw.orders_ext`
with partition columns (ingest_date date)
options (
    format = 'PARQUET',
    uris = ['gs://lake/raw/orders/*'],
    hive_partition_uri_prefix = 'gs://lake/raw/orders'
);
```

```yaml
# dbt 에서는 source() 로 가리키기만 하면 된다 — 모델 코드는 바뀌지 않는다
sources:
  - name: raw
    tables:
      - name: orders_ext
```

- **실무 판단**: **자주 읽히면 적재하고, 가끔 읽히면 외부 테이블로 둠**
  - staging에서 한 번 읽고 마는 원본이면 외부 테이블이 합리적임


## 7-5. 스키마 드리프트

### 7-5-1. 정의

- 원천 스키마가 예고 없이 바뀌는 것
- 세 가지 형태가 있음

| 변경 | 위험도 | 대응 |
|---|---|---|
| **컬럼 추가** | 낮음 | 랜딩은 그대로 수용. staging에서 명시적으로 선택 |
| **컬럼 삭제** | 높음 | staging이 즉시 깨짐 → 테스트로 조기 감지 |
| **타입 변경** | **가장 위험** | 조용히 값이 틀어짐. 캐스팅 실패나 정밀도 손실 |

- **원칙: 랜딩은 관대하게, staging은 엄격하게**
  - 랜딩에서 스키마를 강제하면 원천이 바뀔 때마다 수집이 멈춤
  - 반대로 staging에서 느슨하면 **틀어진 값이 조용히 downstream로 퍼짐**

- `SELECT *`를 staging에서 쓰지 않는 이유가 이것임
- 컬럼을 명시해야 사라졌을 때 즉시 깨짐
